--- FRONTMATTER ---
name: docstruct
description: Quản lý và tạo cấu trúc tài liệu dự án theo mô hình Atomic
Content Blocks. Kích hoạt khi user muốn khởi tạo cấu trúc tài liệu cho dự án mới,
tổ chức/refactor tài liệu đang tồn tại, tổng hợp tài liệu hoàn chỉnh (BRD, PRD,
SAD, FSD...), review phản biện một vấn đề/file qua subagent, hoặc quản lý bộ nhớ
kiến thức project qua remember/knowledge. Gõ /docstruct không tham số để quét
dự án và chọn thao tác tiếp theo.

================================================================================
1. TỔNG QUAN
================================================================================

`docstruct` tổ chức tài liệu dưới dạng **Atomic Content Blocks (Khối Nội dung
Nguyên tử)**: mỗi mục nhỏ là một file markdown riêng biệt, viết đúng một lần
(Single Source of Truth), sau đó lắp ghép thành tài liệu hoàn chỉnh (BRD, PRD,
SAD, FSD...).

Điểm mạnh:
- **Chuẩn hóa:** mọi dự án có cấu trúc tài liệu giống nhau, dễ đối chiếu chất lượng.
- **Nguyên tử:** mỗi block là một đối tượng riêng — dễ phân công, theo dõi trạng
  thái, quản lý phiên bản.
- **Linh hoạt:** tài liệu đầu ra chỉ là các "View" được tổng hợp từ cùng tập block
  gốc theo **Aggregation Matrix** (Mục 7).
- **Bộ nhớ kiến thức:** fact của project (business, technical, team...) lưu thành
  file nhỏ theo domain dưới `.docstruct/knowledge/` và load chọn lọc như RAG.

================================================================================
1.1 KNOWLEDGE NHƯ RAG CHỌN LỌC (không cần vector DB)
================================================================================

Vì không có vector search, knowledge được tổ chức để truy xuất qua filename + index:

- Mỗi fact lưu trong file đặt tên theo domain: `business-*.md`, `technical-*.md`,
  `team-*.md`, `common-*.md`, `security-*.md`... Agent tự chọn tên phù hợp nhất
  với nội dung để có thể tìm mà không cần load toàn bộ.
- `.docstruct/knowledge/_index.md` là bảng tra duy nhất: mỗi file một dòng
  `file | domain | summary | tags`. Agent chỉ đọc `_index.md` (nhỏ) để quyết định
  file nào cần load cho task hiện tại, rồi chỉ load những file đó. Không load toàn
  bộ `knowledge/` mặc định.
- Dùng `_index.md` trước mọi lượt `init`, `generate` cần context:
  đọc `_index`, chọn dòng có domain/tags khớp task (vd business cho BRD, technical
  cho SAD), chỉ load file khớp. Knowledge thắng default khi xung đột.

================================================================================
2. WORKSPACE `.docstruct/`
================================================================================

Skill lưu toàn bộ cấu hình và trạng thái vào `.docstruct/` tại gốc dự án:

.docstruct/
├── project-profile.yaml   # Hồ sơ dự án: loại, audience, doc-root, cấu hình ngôn ngữ, schema_version
├── schema.yaml            # Cây thư mục đã duyệt + ma trận tổng hợp (+ schema_version)
├── agents.yaml            # Cấu hình subagent review ("đệ tử") — xem Mục 10
├── status/                # Trạng thái: DRAFT | UPDATING | RELEASED
├── knowledge/             # Bộ nhớ kiến thức - RAG chọn lọc (xem Mục 4)
│   ├── _index.md          # Tra cứu: file | domain | summary | tags
│   ├── business-*.md
│   ├── technical-*.md
│   ├── team-*.md
│   └── common-*.md
├── elicitation/           # Q&A tạm cho generate (xem Mục 6)
│   └── <sanitized-path>.md
└── reviews/               # Báo cáo review đã lưu: RR-YYYYMMDD-HHmmss-<slug>.md (xem Mục 10)

> QUAN TRỌNG: `project-profile.yaml` ghi rõ **doc-root** — vị trí lưu tài liệu do
> user chọn khi chạy `init`. Mọi lệnh (generate, remember, knowledge) phải
> đọc config này trước khi thao tác. Tuyệt đối không suy đoán doc-root.

> CẤU HÌNH NGÔN NGỮ: `project-profile.yaml` cũng ghi **ngôn ngữ trả lời**
> (`language.response`) và **ngôn ngữ tài liệu** (`language.documentation`). Đây
> là nguồn sự thật duy nhất cho mọi quyết định giao tiếp và nội dung — xem Mục 9.
> Nếu trống hoặc thiếu, phải hỏi user trước khi chạy lệnh nào.

> BỘ NHỚ RAG: Trước mọi lượt `init`, `generate` cần context,
> đọc `.docstruct/knowledge/_index.md` (nếu tồn tại), rồi chỉ load file knowledge
> có domain/tags khớp task. Dùng knowledge làm ground truth khi xung đột. Xem Mục 4.

> ELICITATION & STATUS: `generate` lưu Q&A tạm tại `.docstruct/elicitation/` và
> đánh trạng thái mỗi file `DRAFT | UPDATING | RELEASED` (frontmatter `status:` +
> `.docstruct/status/`). Xem Mục 6.

3. LỆNH `/docstruct` (không tham số) - QUÉT DỰ ÁN + DASHBOARD + CHỌN THAO TÁC
================================================================================

Khi user chạy `/docstruct` không tham số, hoặc tham số không khớp lệnh nào, KHÔNG
thực thi workflow. Thay vào đó chạy **quét sâu chỉ-đọc** rồi hiện dashboard + popup
chọn thao tác:

1. **Quét sâu (read-only)** -
   - Nếu `.docstruct/project-profile.yaml` và `schema.yaml` tồn tại: đọc `docroot`,
     `language.*`, `schema_version`; liệt kê cây thực tế dưới doc-root (mỗi folder
     00-common -> 99-assets: tồn tại/thiếu, số file, breakdown DRAFT/UPDATING/RELEASED
     từ frontmatter `status:` + `.docstruct/status/`).
   - Nếu chưa init: hiện `Not initialized` và preview cây chuẩn từ Mục 8.
   - Kiểm tra knowledge: nếu `.docstruct/knowledge/_index.md` tồn tại, hiện
     `Knowledge: N files` và 5 dòng đầu; nếu không, hiện `Knowledge: (empty)`.
   - Kiểm tra agents: nếu `.docstruct/agents.yaml` tồn tại, hiện
     `Agents: <ids> (default: <id>)`; nếu không, hiện `Agents: (default inline critic)`.
   - Quét nhẹ repo: README (domain, tính năng chính), cây source top-level + tín hiệu
     tech stack (package.json / requirements / go.mod / pom.xml / Cargo.toml...),
     ước lượng quy mô code, file docs nằm ngoài doc-root (nếu có).
   - Tổng hợp **Project Note**: 5-8 dòng hiện trạng — đã init?, doc-root, coverage
     docs (% RELEASED), gap lớn nhất (top-3 folder/file trống), tech stack, độ sâu knowledge.
2. **Tóm tắt lệnh:**

    | Lệnh | Khi nào dùng | Ví dụ |
    |------|-------------|-------|
    | `/docstruct init <mô tả>` | Khởi tạo cấu trúc 12 folder, hoặc re-init / migrate nếu đã init | `/docstruct init E-commerce Next.js + PostgreSQL` |
    | `/docstruct generate` | Xây file tiếp theo theo thứ tự (hỏi theo role) | `/docstruct generate` |
    | `/docstruct generate <file>` | Tập trung vào file chỉ định | `/docstruct generate 02-business/01-value-prop.md` |
    | `/docstruct review <chủ đề\|file>` | Review phản biện vấn đề/file qua subagent | `/docstruct review Có nên dùng microservices?` |
    | `/docstruct remember <text tự do>` | Ghi kiến thức (phân tích -> confirm -> lưu) | `/docstruct remember STID là công ty` |
    | `/docstruct knowledge` | Liệt kê knowledge | `/docstruct knowledge` |
    | `/docstruct config [agents\|conventions\|language]` | Hub cấu hình: subagent review, quy ước, ngôn ngữ | `/docstruct config` |

3. **Hiện Aggregation Matrix rút gọn** - BRD/PRD/SAD/FSD từ Mục 7.
4. **Popup chọn thao tác** — sau dashboard luôn hỏi user làm gì tiếp (dùng question/picker
   nếu có, không thì list đánh số). Đề xuất sẵn **2-3 gợi ý thông minh** theo hiện trạng, vd:
   - Chưa init → gợi ý `init`.
   - `01-overview` / `02-business` trống → gợi ý `generate <file đó>`.
   - Nhiều file `RELEASED` nhưng chưa review → gợi ý `review <chủ đề>`.
   - Knowledge trống → gợi ý `remember <facts>`.
   User được chọn gợi ý hoặc gọi lệnh khác. KHÔNG tự chạy side-effect khi chưa qua
   confirm của lệnh đó.
5. **Không tạo/sửa file.** Nếu token đầu không khớp (vd `/docstruct foo`), prefix
   `Unknown command 'foo'. Valid: init, generate, review, remember, knowledge, config.`
   và gợi ý gần đúng. Alias `help`, `--help`, `-h` cũng hiện dashboard. So khớp
   case-insensitive.

================================================================================
4. LỆNH `/docstruct remember / knowledge` - BỘ NHỚ KIẾN THỨC (RAG CHỌN LỌC)
================================================================================

File kiến thức là fact chuẩn mà agent phải nhớ và tuân theo. Lưu thành file nhỏ
theo domain để load chọn lọc mà không cần đọc toàn bộ.

### Lưu trữ

.docstruct/knowledge/
├── _index.md          # file | domain | summary | tags - chỉ file này đọc mặc định
├── business-*.md
├── technical-*.md
├── team-*.md
├── common-*.md
└── security-*.md

`_index.md` format (mỗi file một dòng):

| file | domain | summary | tags |
|------|--------|---------|------|
| business-stid-team.md | business | STID là công ty, PM là Hảo, member Hảo/Vu/Dai | stid, team, pm |
| technical-stack.md | technical | Stack: Next.js + PostgreSQL | nextjs, postgres |

Domain: `business`, `technical`, `team`, `common`, `security`, `quality`,
`operations`, `guides` - chọn gần nhất. Agent tự chọn tên file khớp nội dung nhất
(vd `business-stid-team.md` cho fact về team) để tìm mà không load toàn bộ. Mỗi
file giữ 1-3 fact; nếu user nói nhiều domain thì tách thành nhiều file.

### Load chọn lọc (RAG không vector DB)

Trước mọi lượt `init`, `generate` cần context:

1. Đọc `knowledge/_index.md` nếu tồn tại (nhỏ, luôn đọc).
2. Chỉ chọn dòng có `domain`/`tags`/`summary` khớp task hiện tại (vd `business` cho
   BRD/Proposal, `technical`+`architecture` cho SAD/FSD, `team` cho task liên quan
   con người).
3. Chỉ load file knowledge khớp. KHÔNG load toàn bộ `knowledge/`.

Knowledge là ground truth: khi knowledge xung đột với code/README scan, ưu tiên
knowledge.

### Subcommands

| Subcommand | Hành vi |
|------------|---------|
| `remember <text tự do>` | **Phân tích -> confirm -> lưu.** Parse text, tách fact riêng, viết lại mỗi fact thành câu chuẩn (văn current-state Mục 9, không lịch sử), chọn tên file domain cho mỗi fact, hiện preview bảng `file | nội dung chuẩn` + dòng `_index` sẽ thêm. Hỏi `Confirm? (yes / edit <sửa>)`. Chỉ khi `yes` (hoặc sau `edit` và yes lại) mới ghi file và cập nhật `_index.md`. Nếu user nói `edit`, render lại preview đã sửa và hỏi lại. `knowledge <text>` là alias của lệnh này. Không giữ backward. |
| `knowledge` | **Liệt kê** (không tham số). Đọc `_index.md` và render bảng + số file. Nếu `_index` thiếu nhưng file tồn tại, rebuild từ tên file. Read-only. |

Unknown subcommand cho nhóm này -> `Unknown command 'X'. Valid: remember <text>, knowledge.` rồi hiện bảng. `help`/`--help`/`-h` cũng hiện.

### Ví dụ

```
/docstruct remember STID là công ty tôi, tôi là PM, member gồm Hảo (tôi), Vu (Backend) và Dai (Frontend)
/docstruct knowledge
```

================================================================================
5. LỆNH `/docstruct init <mô tả dự án>`
================================================================================

Khởi tạo cấu trúc tài liệu cho một dự án. Xử lý cả init mới và re-init khi đã init rồi.

### 5.1 PHÁT HIỆN TRẠNG THÁI HIỆN TẠI

1. **Quét trước** — quét sâu như Mục 3: README, cây source + tech stack, docs hiện có
   (trong và ngoài doc-root), trạng thái `.docstruct/` (project-profile.yaml,
   schema.yaml, `schema_version`, số file knowledge, config agents).
2. **Nếu `.docstruct/` đã tồn tại** (re-init) — hiện cái đang có (profile,
   schema_version, doc-root, số file docs, knowledge N files) và hỏi:
   - `[1] Override — xây lại từ đầu` (`.docstruct` + cây docs mới từ templates)
   - `[2] Migrate / Upgrade — cập nhật tại chỗ, giữ nội dung` (khuyên dùng khi
     docs/knowledge đã có giá trị)
   - `[3] Hủy`
   KHÔNG làm tiếp khi chưa có lựa chọn rõ ràng.
3. **Nếu chưa init** — đi tiếp quy trình chuẩn §5.2.

### 5.2 QUY TRÌNH CHUẨN (init mới)

1. **Quét dự án** — đọc README, mã nguồn (cấu trúc cây, công nghệ chính), tài
   liệu hiện có (nếu có) để tổng hợp bối cảnh: domain nghiệp vụ, tính năng chính,
   quy mô code, ràng buộc kỹ thuật.
2. **Hỏi chủ động để làm rõ** — đặt câu hỏi cho user kèm gợi ý dựa trên kết quả quét:
   - Mục tiêu sản phẩm/giải pháp
   - Đối tượng tài liệu (kỹ sư, quản lý, khách hàng...)
   - Phạm vi và độ sâu kỹ thuật
   - Yêu cầu bảo mật/tuân thủ đặc thù (nếu có)
   - Các loại tài liệu đầu ra cần có (BRD, PRD, SAD...)
   - **Ngôn ngữ trả lời** — ngôn ngữ agent dùng khi hội thoại: `en` hoặc `vi`
     - **Ngôn ngữ tài liệu** — ngôn ngữ nội dung tài liệu: `en`, `vi`, hoặc
       `vi-en` (định nghĩa tại Mục 10)
3. **Hỏi vị trí lưu tài liệu (doc-root)** — user chọn:
   - `docs/` (thư mục tài liệu truyền thống), hoặc
   - `.docstruct/docs/` (gói gọn trong workspace của skill)
3b. **Chốt quy ước (gọn 4-6 câu)** — Phần A (cố định do skill áp: naming file, SSOT,
   vòng đời status, ngôn ngữ, images, quy tắc file auto) được seed từ
   `templates/conventions.md`, không hỏi; chỉ hiện preview read-only. Chỉ hỏi Phần B
   (đặc thù dự án) kèm default suy từ scan:
   - Diagram tool: `mermaid | plantuml | drawio` (+ fallback image)
   - API spec format: `openapi-yaml | md-table | both`
   - Tone & độ sâu: `high-level | balanced | deep-dive` (sync `audience.technical_depth`)
   - Người duyệt RELEASED: một tên/role, hoặc duyệt theo domain
   - Thuật ngữ khóa: tên sản phẩm/thương hiệu giữ nguyên cách viết, hoặc `(none)`
   - Deliverable ưu tiên: BRD/PRD/SAD/... nào trước, hoặc `(all)`

   Mục nào bỏ trống thì dùng default đã ghi rõ. Ghi `00-common/01-conventions.md` ngay
   (status RELEASED, nguồn duy nhất dạng MD — không mirror sang YAML).
4. **Xác nhận dàn ý** — trình bày cây thư mục + danh sách file cụ thể (đã gồm quy ước
   vừa chốt), chờ user duyệt. Nếu dự án đã có tài liệu không theo schema, đề xuất luôn
   phương án sắp xếp lại (bảng mapping `old path → new path | giữ / di chuyển / archive
   vào 99-assets/_legacy/`) trong bước này.
5. **Khởi tạo** — sau khi duyệt:
   - Tạo `.docstruct/project-profile.yaml` và `.docstruct/schema.yaml`
     (từ template trong thư mục `templates/` của skill) với `schema_version: 1`,
     bao gồm cả `language.response` và `language.documentation` đã chọn
   - Tạo `.docstruct/agents.yaml` từ `templates/agents.yaml` nếu chưa có (không bao
     giờ ghi đè file đã tồn tại khi chưa hỏi)
   - Ghi `00-common/01-conventions.md` từ `templates/conventions.md` với giá trị Phần B
     từ bước 3b; tạo `02-references.md`, `03-abbreviations.md`, `04-glossary.md`,
     `05-traceability.md` dạng placeholder ghi `auto-populated by generate — do not edit manually`
   - Tạo cây thư mục theo dàn ý, mỗi thư mục có `README.md` mô tả phạm vi
   - Tạo README tổng quan tại doc-root kèm lộ trình đọc

### 5.3 RE-INIT: OVERRIDE vs MIGRATE

**Backup trước (bắt buộc cả 2 nhánh):** trước khi đụng vào gì, copy `.docstruct/` +
cây doc-root sang `.docstruct.backup-<YYYYMMDD-HHmmss>/` và báo đường dẫn backup
trong reply. Backup lỗi thì dừng và hỏi user.

| | Override (xây lại) | Migrate / Upgrade (tại chỗ) |
|---|---|---|
| `project-profile.yaml` | Tạo mới từ template (`schema_version: 1`); hỏi lại language + doc-root | Giữ + merge: giữ `language.*`, `docroot.path`, audience; chỉ điền key thiếu và bump `schema_version` |
| `schema.yaml` | Tạo mới từ template | Cập nhật tại chỗ: thêm folder/file thiếu, giữ tùy biến đã duyệt; đồng bộ `meta.docroot` + `schema_version` |
| `agents.yaml` | Tạo mới từ template chỉ khi thiếu hoặc user đồng ý | Giữ config user; chỉ merge key thiếu (agent id mới, `default_reviewer`) |
| `knowledge/` | **Giữ mặc định** — copy lại từ backup; chỉ bỏ khi user nói rõ | Giữ toàn bộ; rebuild `_index.md` nếu lệch |
| Nội dung docs | Cây mới (file cũ mất khỏi doc-root — vẫn còn trong backup) | Giữ: không xóa file user đã viết; chỉ tạo folder/file + `README.md` còn thiếu |
| `00-common/01-conventions.md` | Ghi từ template với Phần B từ bước 3b | Thiếu: seed Phần A + hỏi Phần B. Đã có: giữ Phần B, chỉ refresh Phần A khi user đồng ý |
| File lệch schema | N/A (mới) | Đề xuất bảng mapping; chỉ move/giữ/archive vào `99-assets/_legacy/` sau khi confirm từng dòng |

Sau cả 2 nhánh, báo cáo: `đường dẫn backup | cái gì được giữ | cái gì xây mới | cái gì cần user rà soát`.

### 5.4 SAU INIT — POPUP LỆNH TIẾP THEO

Khi init (mới, override hay migrate) xong, luôn hiện picker lệnh tiếp theo với **2-3
gợi ý cụ thể** theo trạng thái mới, vd:

- `generate 01-overview/01-problem-statement.md — mục đích nền tảng còn trống`
- `config conventions — tinh chỉnh quy ước nếu bước 3b đã dùng default`
- `remember <fact từ scan> — giữ stack/team facts`

Dùng question/picker nếu có, không thì list đánh số. Chờ user chọn; KHÔNG tự chạy
`generate` khi chưa confirm.

VÍ DỤ:
/docstruct init Dự án e-commerce bằng Next.js + PostgreSQL, đội 3 dev
/docstruct init

Không có mô tả: vẫn quét dự án hiện tại trước, rồi hỏi từ bước 2.

================================================================================
6. LỆNH `/docstruct generate` / `generate <file>` - XÂY DOCS THEO THỨ TỰ (HỎI THEO ROLE)
================================================================================

Xây tài liệu linh hoạt dựa trên thực trạng + vai trò bạn. Hai chế độ:

- `/docstruct generate` — đề xuất 2-3 file tiếp theo để xây, dựa trên thực trạng, không cứng nhắc.
  Bỏ qua toàn bộ `00-common` — `01-conventions.md` đã chốt lúc `init` (bước 3b),
  `02-05` auto-populate; điểm bắt đầu viết là `01-overview`.
- `/docstruct generate <file>` — tập trung vào file chỉ định (vd `02-business/01-value-prop.md`
  hoặc `10-deliverables/01-BRD.md`) để tạo hoặc điều chỉnh. Nếu file đã `RELEASED`,
  cảnh báo và hỏi có update không.

### Thứ tự chuẩn

Thứ tự là `00-common -> 01-overview -> 02-business -> 03-features -> 04-architecture
-> 05-security -> 06-implementation -> 07-quality -> 08-operations -> 09-guides
-> 10-deliverables -> 99-assets` như trong `schema.yaml` và Mục 8. Trong mỗi folder,
file xếp theo prefix số. Thứ tự này là tham chiếu, không phải gate cứng: dùng để hiểu
tiền đề (vd `01-overview` và `02-business` là tiền đề cho `04-architecture`), nhưng
không chặn linh hoạt. Nếu tất cả đã `RELEASED`, trả `Tất cả đã hoàn thiện.`.

### Lưu elicitation

Q&A tạm lưu tại `.docstruct/elicitation/<sanitized-path>.md` (vd
`02-business-01-value-prop.md`) để đỡ context. Chỉ đọc khi cần trong `generate`.
Sau khi xong file chính, hỏi user giữ hay xóa file elicitation.

### Trạng thái

Mỗi file docs có `status:` ở frontmatter và mirror tại `.docstruct/status/<path>`:

- `DRAFT` — file mới hoàn toàn, version đầu tiên.
- `UPDATING` — đã có nội dung tham khảo và đang chỉnh sửa.
- `RELEASED` — đã hoàn thiện, có thể dùng làm cơ sở cho file khác, không sửa.
  Nếu `generate <file>` nhắm vào `RELEASED`, báo `File đã RELEASED` và hỏi
  `Update? (yes/no)`. Nếu `yes`, đổi thành `UPDATING` rồi mới sửa.

Không giữ backward: mọi tạo mới/điều chỉnh đều coi như version đầu tiên (Mục 9).

### QUY TRÌNH

1. **RAG chọn lọc** — đọc `knowledge/_index.md` (nếu có), chọn dòng có
   domain/tags khớp file đích (`business` cho BRD, `technical`+`architecture` cho
   SAD, `team` cho người), chỉ load file khớp.
2. **Hỏi bạn là ai & đề xuất file theo thực trạng:**
   - Hỏi trước: `Bạn là ai trong dự án này? Vai trò gì? (customer / sales / BA / dev / PM)
     — bạn nắm gì nhất?` Lưu vào `knowledge/team-role.md` nếu chưa có (lần sau chỉ
     xác nhận `Vẫn là <role>?`), và vào `elicitation/<target>.md`.
    - Quét thực trạng: file nào thiếu/trống (`DRAFT`), `UPDATING`, `RELEASED`,
      `change-requests/CR-*.md` mới. Dùng order chuẩn làm tham chiếu để hiểu tiền đề
      (vd `01-overview` và `02-business` là tiền đề cho `04-architecture`), nhưng
      **không cứng nhắc** — hiểu linh hoạt cái gì thực sự cần. Bỏ qua toàn bộ
      `00-common` (`01-conventions.md` đã chốt lúc init, `02-05` auto); điểm bắt đầu viết
      là `01-overview`, không phải `00-common`.
   - Nếu có `<file>`: coi như bạn muốn file đó, nhưng nếu nó phụ thuộc tiền đề chưa
     xong (vd nhắm `04-architecture` trong khi `01-overview/03-goals.md` còn trống),
     giải thích vì sao tiền đề quan trọng và hỏi `Bạn muốn tiếp tục file này hay
     chuyển sang tiền đề?`.
   - Nếu không có `<file>`: đề xuất **2-3 ứng viên** cho file tiếp theo, mỗi cái
     kèm lý do 1 dòng (vd `1. 01-overview/01-problem-statement.md — mục đích nền tảng
     còn trống; 2. 02-business/01-value-prop.md — business cần trước architecture`).
     Để bạn chọn. Bạn cũng có thể chỉ định file khác.
   - Khi đã chọn/chốt đích, đọc nội dung hiện có (nếu `UPDATING`) và file lân cận
     cùng folder + glossary.
3. **Hỏi chi tiết linh hoạt theo role+thực trạng:**
   - Sinh **~5 câu hỏi** dựa trên `role + domain file + thực trạng` (vd
     `02-business/*` với customer -> market/pain/SLA/metrics; `04-architecture/*`
     với customer -> chỉ hỏi flow/business rule, với dev mới hỏi endpoint/schema/
     NFR/diagram). **Không hỏi khách hàng về code**, nhưng không áp rule cứng
     "mục đích trước technical" cho mọi case.
   - Append Q&A vào elicitation file. Phân tích thiếu field nào của file đích
     (theo schema) còn thiếu gì → hỏi tiếp 3-5 câu bổ sung, append, lặp đến khi đủ.
4. **Đề xuất outline** — liệt kê section cho file đích, ghi chú nguồn
   (block/folder và file knowledge nào). Chờ duyệt.
5. **Viết** — tạo/cập nhật file đích trong folder chuẩn (kebab-case + prefix số,
   Mục 9) bằng văn current-state (Mục 9, không backward). Tuân thủ Phần B của
   `00-common/01-conventions.md` (diagram tool, API format, tone, thuật ngữ khóa);
   nếu conventions thiếu chỉ dẫn cho file này thì dùng default hợp lý và ghi chú 1 dòng,
   không tự sửa conventions. Cập nhật `status:` thành `DRAFT` hoặc `UPDATING`.
   Nếu có fact mới, cập nhật `knowledge/` nếu cần.
6. **Tự động cập nhật 00-common** — ngay sau khi viết, quét nội dung mới để tìm
   thuật ngữ, viết tắt, reference chưa có trong `00-common/`. Tự động append vào
   file tương ứng mà không cần lệnh khác:
   - Thuật ngữ mới → append vào `00-common/04-glossary.md` với định nghĩa 1 dòng
     suy từ context; nếu `vi-en` thì thêm gloss tiếng Anh.
   - Viết tắt mới → append vào `00-common/03-abbreviations.md`.
   - Reference ngoài mới → append vào `00-common/02-references.md`.
   Không cần confirm; chỉ ghi chú `Auto-updated 00-common: +2 terms, +1 abbreviation.`
   trong reply. Deduplicate trước khi append và vẫn auto-append ngay cả khi file
   `00-common` đã `RELEASED` (vì đây là tham chiếu sống).
7. **Dọn elicitation** — hỏi `Giữ file elicitation để tra cứu hay xóa? (keep / delete)`.
8. **Confirm & đánh trạng thái** — hỏi `Đánh trạng thái file là? (DRAFT / UPDATING / RELEASED)`.
   Mặc định `RELEASED` nếu user nói đã xong. Cập nhật frontmatter và
   `.docstruct/status/<path>`. `RELEASED` mới được tham chiếu bởi `generate` sau.
9. **Popup lệnh tiếp theo** — sau khi đánh trạng thái luôn hỏi làm gì tiếp (picker nếu
   có, không thì list đánh số). Đề xuất 2-3 ứng viên cụ thể theo thực trạng mới (tiền đề
   + gap), mỗi cái kèm lý do 1 dòng, cộng thêm `review <file vừa xong>` và `dừng`. Chờ
   user chọn; KHÔNG tự chạy.

9. QUY TẮC BIÊN SOẠN
================================================================================

1. **Single Source of Truth:** mỗi nội dung chỉ viết một lần tại một file duy nhất;
   tài liệu tổng hợp chỉ ghép, không sao chép nội dung.
2. **Cấu hình ngôn ngữ** — đọc từ `project-profile.yaml`
   (`language.response`, `language.documentation`):
   - **Phản hồi hội thoại** (câu hỏi làm rõ, Q&A elicitation, đề xuất dàn ý...)
     dùng `language.response`.
   - **Nội dung tài liệu** dùng `language.documentation`, định nghĩa:

     | Chế độ | Định nghĩa | Ví dụ |
     |--------|-----------|-------|
     | `en`   | Thuần tiếng Anh | — |
     | `vi`   | Thuần Việt; chỉ giữ nguyên tiếng Anh cho TÊN RIÊNG / tên sản phẩm / công nghệ không có bản dịch (code, Java, PostgreSQL, REST API...) | "Hệ thống chạy trên PostgreSQL" |
     | `vi-en`| Tiếng Việt kèm chú thích tiếng Anh trong ngoặc ở LẦN DÙNG ĐẦU của mỗi thuật ngữ chuyên ngành; đăng ký các thuật ngữ đó vào `glossary.md` | "Cơ sở dữ liệu (database) lưu trữ hồ sơ" |

     Phân biệt hai chế độ cuối: `vi` giữ từ tiếng Anh vì KHÔNG CÓ từ Việt tương
     đương; `vi-en` chủ động kèm gốc tiếng Anh để DẠY THUẬT NGỮ, giúp người đọc
     tra cứu thêm.
   - **Fallback:** nếu cấu hình ngôn ngữ trống hoặc thiếu → PHẢI hỏi user quyết
     định trước khi chạy lệnh nào. Tuyệt đối không tự suy đoán mặc định.
3. **Ghi trạng thái hiện tại, không ghi thay đổi - không giữ backward:** khi tạo
   mới hoặc cập nhật block/tài liệu (dù tạo mới hay điều chỉnh), luôn coi như
   **phiên bản đầu tiên**. Viết nội dung cuối cùng như thể viết lại từ đầu hôm nay.
   Tài liệu mô tả sự vật ĐANG NHƯ THẾ NÀO, không mô tả CHÚNG ĐÃ THAY ĐỔI RA SAO.
   TUYỆT ĐỐI không giữ backward: không đề cập backward, previous version, migration
   từ bản cũ, hay lịch sử phiên bản. Cấm trong thân tài liệu các câu kiểu "đã cập
   nhật...", "đã bổ sung...", "đã loại bỏ...", "không còn áp dụng...", "trước đây...",
   "backward compatible", "previous version", "migration". Không nhúng lịch sử
   phiên bản, ghi chú sửa đổi hay mục "có gì mới" vào bất kỳ đâu — việc kiểm soát
   phiên bản do **git đảm nhiệm**.

   | Sai (trong nội dung) | Đúng |
   |----------------------|------|
   | "Đã bổ sung tính năng thanh toán vào module hóa đơn." | "Module hóa đơn bao gồm tính năng thanh toán..." |
   | "Phần báo cáo cũ đã bị loại bỏ ở phiên bản này." | *(xóa hẳn đoạn đó, không để lại dấu vết)* |

4. **Không trùng lặp:** kiểm tra glossary trước khi định nghĩa thuật ngữ mới.
5. **Tên file:** kebab-case kèm tiền tố số thể hiện thứ tự đọc — ví dụ
   `01-problem-statement.md`.
6. **Hình ảnh/sơ đồ:** lưu tại `99-assets/`, tham chiếu bằng đường dẫn tương đối;
   không nhúng base64 inline.
7. **Vòng đời block:** mỗi block có trạng thái `draft → review → approved`, quản
   lý tại `.docstruct/status/`; chỉ block `approved` được đem vào tài liệu tổng
   hợp mà không cần xem lại.
8. **README con:** mọi thư mục phải có `README.md` mô tả phạm vi và danh sách file.

================================================================================
10. LỆNH `/docstruct review <chủ đề|file>` - REVIEW PHẢN BIỆN QUA SUBAGENT
================================================================================

Nghiên cứu, phân tích và đánh giá khách quan một vấn đề, ý tưởng hoặc file docs
bằng tư duy phản biện và logic. Skill điều phối subagent review ("đệ tử"), rồi tổng
hợp các báo cáo thành một verdict + đề xuất tiếp theo. **Chỉ-đọc với docs**: không
bao giờ sửa file được review; chỉ lưu báo cáo vào `.docstruct/reviews/` khi đã hỏi.

CÚ PHÁP:

/docstruct review Có nên dùng microservices cho dự án này?
/docstruct review 04-architecture/02-components.md
/docstruct review --no-agents Mô hình pricing hiện tại có lỗ hổng

QUY TRÌNH:

1. **Parse đích + load context (RAG chọn lọc)** — đọc `knowledge/_index.md` (nếu có),
   chỉ load dòng có domain/tags khớp chủ đề. Nếu đích là đường dẫn docs: đọc file đó +
   file lân cận cùng folder + glossary. Nếu là text tự do: quét nhẹ repo + doc-root tìm
   bằng chứng liên quan. Nêu rõ `sources: ...` để reviewer trích dẫn được.
2. **Chốt reviewer từ `.docstruct/agents.yaml`:**
   - Thiếu file: dùng 1 `critic` inline với prompt mặc định từ `templates/agents.yaml`
     (chế độ single-critic).
   - Có file: hiện agents đang enabled (`id | role`), cho user multi-select (picker nếu
     có, không thì list đánh số). Pre-select `default_reviewer`. Mặc định là **1 critic**;
     chỉ chạy multi-agent khi user chọn 2+ agents hoặc chủ đề cần cả research + phản biện.
   - Cờ `--no-agents` ép chạy single inline critic, bỏ qua config (để debug).
   - Nếu runtime không có cơ chế subagent (không có Task tool): **fallback inline** — chạy
     tuần tự từng reviewer trong context hiện tại, gắn nhãn `Reviewer <id> (inline
     fallback)`, rồi tổng hợp. Không fail chỉ vì thiếu subagent.
3. **Điều phối reviewer** — mỗi reviewer nhận: nội dung chủ đề/file, tóm tắt context, và
   `role + prompt` riêng từ `agents.yaml`. Bắt buộc trả về cấu trúc:
   - `findings:` list (nhận định → bằng chứng `file:line` hoặc `knowledge/<file>`)
   - `counter-arguments:` góc nhìn đối lập mạnh nhất
   - `verdict:` agree | conditionally-agree | disagree + lý do
   - `confidence:` high/medium/low cho từng finding
   - `open questions:` bằng chứng nào còn thiếu
   Chạy song song các agents khi runtime hỗ trợ.
4. **Tổng hợp (skill làm, không phải subagent)** — đối chiếu các báo cáo thành:
   - `Consensus:` điểm mọi reviewer đồng ý
   - `Conflicts:` điểm bất đồng (ai nói gì)
   - `Missing evidence:` cái gì sẽ chốt được mâu thuẫn
   - `Overall verdict:` agree | conditionally-agree | disagree + rationale 3-5 dòng
   - `Risks & alternatives:` list ngắn
   Trả lời bằng `language.response`. Khách quan: báo cáo trung thực bất đồng, không giấu.
5. **Lưu báo cáo (phải hỏi trước)** — hỏi `Lưu báo cáo review vào .docstruct/reviews/?
   (save / skip)`. Nếu `save`, ghi `.docstruct/reviews/RR-YYYYMMDD-HHmmss-<slug>.md` với
   frontmatter (`topic, verdict, reviewers, date, sources`) + synthesis + tóm tắt từng
   reviewer. Không lưu khi chưa hỏi.
6. **Popup tiếp theo** — sau synthesis luôn đề xuất follow-up (picker nếu có): vd
   `generate <file liên quan>`, `remember <fact mới lộ ra>`, `review lại với thêm bằng
   chứng`, `dừng`. Chờ pick; KHÔNG tự chạy.

VÍ DỤ:

/docstruct review Có nên dùng microservices cho dự án này?
/docstruct review 05-security/01-threat-model.md
/docstruct review --no-agents SLA hiện tại có thực tế không?

================================================================================
11. LỆNH `/docstruct config` - HUB CẤU HÌNH (agents | conventions | language)
================================================================================

Hub tập trung cho cấu hình skill. Ba nhánh, không có `doc-root` ở đây (đổi doc-root
là migrate nặng — giữ trong `init`).

### 11.1 HUB (không tham số)

/docstruct config               → picker hub (chỉ-đọc cho đến khi chọn nhánh)
/docstruct config agents        → vào thẳng §11.2
/docstruct config conventions   → vào thẳng §11.3
/docstruct config language      → vào thẳng §11.4

QUY TRÌNH:

1. Đọc state: `agents.yaml` (có? N enabled, default?), Phần B của
   `00-common/01-conventions.md` (bảng 6 giá trị hoặc `missing`),
   `language.response/documentation` từ `project-profile.yaml`.
2. Hiện picker (picker tool nếu có, không thì list đánh số), mỗi dòng kèm 1 dòng trạng thái:
   - `1. agents — subagent review (N enabled, default: <id>)`
   - `2. conventions — quy ước đặc thù (diagram, API format, tone, approver...)`
   - `3. language — ngôn ngữ trả lời + ngôn ngữ tài liệu`
3. Vào nhánh được chọn. Xong nhánh thì hỏi `về hub / dừng`. Arg lạ →
   `Unknown command 'config X'. Valid: agents, conventions, language.` rồi hiện hub.

### 11.2 NHÁNH: agents - QUẢN LÝ SUBAGENT REVIEW

Quản lý cấu hình `.docstruct/agents.yaml`:

1. Thiếu file thì tạo từ `templates/agents.yaml` của skill rồi hiện nội dung.
2. Có file thì liệt kê `id | role | enabled | default?`.
3. Cho chọn thao tác (picker nếu có, không thì list số): `thêm agent | sửa role/prompt |
   bật / tắt | đặt default_reviewer | reset từ template (hỏi trước khi ghi đè prompt custom)`.
4. Sau đổi, render lại list và nhắc `/docstruct review` sẽ offer các agents này để chọn.
   `init` không bao giờ ghi đè `agents.yaml` đã có khi chưa hỏi (chỉ merge key thiếu) —
   xem Mục 5.3.

### 11.3 NHÁNH: conventions - SỬA QUY ƯỚC ĐẶC THÙ

Sửa Phần B của `00-common/01-conventions.md` (Phần A do skill cố định):

1. Hiện Phần B hiện tại dạng bảng `mục | giá trị`; Phần A chỉ hiện 6 bullet tiêu đề
   (full text khi user yêu cầu).
2. Cho sửa từng mục (picker nếu có, không thì list số): diagram tool | API format |
   tone & depth | người duyệt RELEASED | thuật ngữ khóa | deliverable ưu tiên. Mỗi mục
   kèm default suy từ scan.
3. `reset` seed lại Phần A từ `templates/conventions.md` và **giữ nguyên Phần B**.
   Confirm trước mọi ghi file.
4. Sau lưu, hỏi `review các file RELEASED chịu ảnh hưởng?` — chỉ gợi ý lệnh `review`,
   không bao giờ tự sửa file RELEASED. `init`/`migrate` không ghi đè Phần B khi chưa hỏi
   (xem Mục 5.3).

### 11.4 NHÁNH: language - NGÔN NGỮ TRẢ LỜI + TÀI LIỆU

1. Hiện `language.response` + `language.documentation` từ `.docstruct/project-profile.yaml`
   (kèm định nghĩa `vi` vs `vi-en` ở Mục 9).
2. Cho đổi với option `en | vi | vi-en` tùy mục; confirm trước khi ghi vào `project-profile.yaml`.
